# 总体架构与接口草案

状态：2026-11-08 用户已确认“先跑通跨 bank MVP，再按实际使用迭代”的方向，并明确工作流效率与模型 token 利用率目标。本轮仅修订文档；下面的接口与策略仍为设计，尚未开发、部署或运行验收。

## 目标与设计取舍

服务帮助动态工作流快速选择怎样调整和推进，并在创建角色/分配任务时，按任务需求与复杂度选择合适的模型类型和推理强度。目标是减少等待、重复上下文整理、无效模型回合和返工，让相同质量的工作消耗更少 token，或在相同预算内取得更多有效进展。

直接建设一个可运行的 MVP，不以前置收益证明、完整标签集、现行基线或 recall 消融阻塞开工。基本联调确认链路能跑通；实际使用中的任务耗时、总 token、纠正和失败用于迭代。单次 API 快、输出短或选了便宜模型，都不能单独证明整条工作流更高效。

首版采用一个进程、一份判断核心、实际需要的 HTTP 或 MCP 入口。受信调用方可直接提交问题、候选项和上下文，常用问题保存成预设，不要求逐场景预审 profile。跨 bank 检索直接进入首版，支持动态工作流、模型配置选择及普通有限答案问题。HTTP/MCP 若都需要则共用核心。

## 数据流

当前任务、候选动作/模型配置与上下文 → 确定入口可读范围 → 选择相关 bank 并行 recall → 整理必要证据 → Decisions 选择候选 → 返回可消费结果、provider 分数与输入来源 → 原工作流/创建者应用并回传 application → 工作单元结果及质量修订回传 result → 精确关联与效果汇总。

检索是首版能力，不是每次调用必经步骤：当前输入已足够时可跳过。优先复用现有结构化状态、能力目录和上下文，避免让本服务先重新写一遍长摘要再判断。

## 两类核心决策

| 决策 | 输入重点 | 返回内容 | 实际应用者 |
| --- | --- | --- | --- |
| workflow_next_action | 当前目标、进度、依赖、最近结果、可用执行能力、预算，以及具体候选动作或调整方案 | 选中的 action/plan candidate_id、对应动作参数及需要回退的状态 | 原项目 workflow / 协调器 |
| role_model_selection | 任务需求与复杂度、已有专业角色要求、宿主实际可用的模型/强度组合、预算与时限 | 选中的配置 candidate_id，映射为模型类型/型号及推理强度 | 原角色创建者 / Herdr 编排入口 |

candidate_id 及参数映射是本服务合同；模型负责有限选择，程序从原候选中取回参数，不把任意生成内容当成可执行命令。此处的专业角色要求不改变组织任职与验收归属。

### 动态工作流如何调整和推进

候选可以包括继续下一步、补一次检查、并行已就绪的独立步骤、在既定策略内重试、调整待办优先级、选择已有替代方案、补充信息或交回负责人；仅将原调用方确实能应用的操作放入当前可执行集合。结果可由原 workflow 消费，不必每次转成人工确认；实际推进仍按原任务授权和执行合同办理。

常见动作和调整方案优先由 workflow 按当前状态给出。需要新增步骤、拆分任务或重排依赖时，规划者提供具体候选方案，本服务帮助选择。workflow 选择同时提供“当前候选均不适合”的非执行出口，由程序映射为 needs_replan、交原规划者补方案，不返回可执行参数。Decisions 的有限答案不能自行生成任意新计划，不能把全部候选生成工作都变成额外的大模型回合。

执行器检查所选动作当前是否可用并应用，保留原任务、步骤、动作和版本关联。会改变运行计划结构的调整应走原 workflow 明确支持的计划更新/接续合同。当前公共模板只消费 WAITING_DECISION 的 choice→step，维持单个活动步骤、不允许返回已完成步骤，也没有通用 fork/join 或运行中改图接口。

因此首个接入由原调用者做 status→快照/候选→服务→decide 的薄适配，服务所选 candidate_id 映射回原 choice；不要把外部模型/检索调用塞进 program 的状态事务。任意动作参数不能直接传给只接受 choice 的 CLI。项目已具备的并行/重试入口可以成为候选，其余计划调整由 Herdr/项目 workflow 侧补应用合同；不修改冻结定义来伪装在途改图，不复制第二套状态机。

### 模型类型与强度怎样匹配任务

先匹配能力，再选择强度。候选由实际宿主/能力目录构建，包含可用模型及其支持的推理强度，必要的工具、模态、上下文长度与已知成本/延迟信息。不能由服务虚构型号、强度档位或可用额度，也不预设所有模型都支持相同档位。现有 Worker 目录能列 provider/model，但尚无统一 reasoning/context/cost 组合合同；Herdr 侧需补候选构建、启动参数映射及实际配置读回，不能把模型名返回当作选型已应用。

复杂度综合看目标歧义、推理与依赖深度、输入规模、领域新颖度、验证难度及最近失败；长文本、专业角色名称或后果严重不单独等同于高复杂度。程序先筛掉不支持所需能力或不符合明确型号/预算约束的组合，再做模型选择；没有可用组合时直接返回 unavailable 及能力缺口，不调用空候选选择或据此任意升档。权限、网络、工具缺失或缺证据不等于推理能力不足，不能统统通过升档重跑解决。

在满足任务能力的候选中，优先选择预计足够完成任务的配置，避免所有角色一律最高档，也避免一律最低档造成重试和返工。首版可用简洁启发式和常用预设直接选型，不等完整模型基准库；后续根据任务完成情况、总 token、耗时和纠正更新策略，不把名义单价当唯一依据。

创建角色或交付新任务时选择一次；任务显著变复杂、连续失败、质量不足或资源条件改变时才重新判断。简单后续单元可降档；升降档在原预算与权限内自动进行，不逐次审批。实际宿主能否热切换由其现有能力决定，不支持时沿下一任务单元或既有交接应用，不能仅因推荐配置已返回就声称角色已切换。

### 何时调用，怎样避免新增无效 token

只在新任务、角色创建、分支歧义、新证据改变候选、依赖变化或需要重规划时调用。固定规则可决定的步骤直接推进，无变化轮询不发模型回合；同一输入与版本复用原结果。只传当前决定需要的状态和检索片段，不每次发送整段工作历史。相互独立的判断可共享同一证据快照；有先后依赖的动作/模型选择仍按实际依赖处理，不能为省调用而使用尚未确定的前提。

## MVP 的逻辑职责

- **问题与预设**：通用 evaluate 接受问题、候选和上下文；预设只减少重复输入，记录实际版本/摘要，不建立逐场景批准台账。
- **证据整理与检索**：复用输入，在允许范围内取相关 bank 的必要片段，保留来源、日期和适用项目。
- **模型调用与结果检查**：处理有限答案 API，检查类型和候选，映射回调用方可消费的动作/配置；使用简单可调处置规则，不等待完整校准。
- **调用与反馈记录**：关联原工作单元的实际采用、执行结果、质量修订及可得 usage/耗时，按事件幂等收回，显示覆盖缺口；人工纠正继续可用，不要求先建完整评价或审计平台。
- **薄接入层**：HTTP/MCP 共用上述核心，沿现有调用者身份和执行入口接入。

以上是职责，不要求分别拆模块、微服务或插件框架。服务模型负责选型，不是它自己创建角色或执行业务动作。

## 跨 bank 检索与项目路由

MVP 使用静态可读 bank 配置。有效范围为服务可读集合与入口/调用者可见集合的交集；同权限受信调用者可共用一份配置，不建动态 ACL 平台、不逐次批准 recall。可直接读取其他项目 bank，无需先搬运到共享库或逐条审批历史经验。

bank_ids 是可选检索选择，不能扩大有效范围；越界选择明确报错。未指定时优先本项目、共享和相关项目，必要时在有效范围内扩大，不默认扫描全库。跨 bank 结果保留 bank/document 来源、日期和适用项目，不直接把不同检索的分数当统一置信度。其他项目经验可供借鉴，不能自动覆盖当前任务明确规则。

来源 project_id 可选，待识别的目标项目是判断结果。未知项目路由从首版支持，使用入口可见的项目目录和相关 bank，不要求先填正确目标项目。实际派发仍由既有协调器按原权限处理。

读取与写入/删除权限分别配置。MVP 反馈保存在服务记录中，无需取得其他 bank 写权限。跨 bank 只读检索不依赖 webhook、可靠增量同步或混合读写权限扩展。

## 建议的公共合同

以下字段为本服务草案，不是 OpenAI 原生请求字段。

最小请求为 question、choices 与 context，或相应 predicate/score 定义，也可引用预设。动作/模型配置作为可定位的候选及元数据提供。可选字段包括 bank_ids、来源 project_id、request_id，以及 workflow 的 subject_ref、状态快照引用、observed_at、evidence_refs。已有原生 state_version 时可透传；当前公共模板没有该字段，薄适配使用实际 source_sha256/input_sha256、step 及相关状态/候选摘要，不能把本服务字段冒称模板原生版本。普通问答无需提供不存在的任务版本，身份由认证入口提供。

响应包含 request_id、decision_id、有类型的 answer、provider 分数、disposition、输入来源、各 bank 检索状态、model 与问题/配置摘要。workflow/model 预设另返回从所选候选取回的动作/配置参数，并回显输入提供的原任务、状态及候选集合版本/摘要，供调用方在原上下文应用。

反馈按[最小回收合同](outcome-feedback.md#最小反馈合同)接收 application/result，关联一个或多个 decision_ids、原工作单元和可得执行引用；人工纠正也可保留。稳定 event_id/revision 区分重投与后补质量更正，原端没有的 run/action/attempt 不强求或伪造。MVP 只需这些轻量记录，不要求后续 Hindsight outcome envelope 的全部字段。

- disposition 为 suggested / abstain / needs_review / needs_replan / unavailable；needs_replan 只用于候选不适合且需原规划者补方案的情况。needs_review 回原负责人或处理路径，不自动向用户申请批准。
- 保留 predicate / choice / score / refusal 的不同语义；输入来源不冒充模型解释或模型证明使用过的引文，规则 reason_codes 由服务记录。
- 无有效建议时不提供可直接执行的答案。空检索或部分 bank 失败可用已有上下文继续并说明缺口；关键证据不足才回退。模型 refusal、非法枚举和接口失败不默认为通过。
- 通用问题可直接调用；预设和 prompt 的普通迭代只需保留实际版本/摘要。初始阈值不宣传为经过校准的准确性保证。
- 显式 request_id 在认证调用方/入口作用域内关联同一份实际输入，包括问题、候选集合及参数/模型配置、predicate/score 定义、上下文、来源项目、检索选择与解析后的预设；同 ID 不同输入报冲突。受理后冻结候选映射，查询/重试返回原映射，不能把旧 candidate_id 用新参数重新解释。服务自己的 ID 不取代业务任务或动作 ID。

### 超时与查询

调用方需要首次响应丢失后定位原请求时，提供自己的 request_id；未提供时服务生成 ID，不承诺客户端丢失响应后仍能定位。get_decision 查询本服务已保存的记录，不能保证找回 provider 未保存的答案。MVP 用同步请求、简单持久记录和可见错误即可，不先建完整后台恢复状态机。

纯判断允许在既定次数、费用和总截止时间内重算，记录独立 attempt 及是否重新推理；同入口重试不重置总预算，完成结果保持冻结。预算耗尽或进程中断导致结果无法确认时明确未知，不伪装恢复或无限等待，也不承诺恰好一次计费。新的证据用新请求，实际业务动作的对账和幂等仍由原执行器承担。

## 最小工具面

- evaluate_decision：通用有限判断，支持跨 bank；提供 workflow_next_action 与 role_model_selection 等少量预设。
- get_decision：只读查询已有判断、应用/结果关联、质量修订和回收缺口，读取范围沿原入口；查询本身不触发补传或业务推进。
- record_decision_feedback：接收适配器直传的 application/result 及带来源纠正，持久化后确认，按事件/修订幂等；不自动写其他 bank 或修改生产策略。

record_decision_outcome、Hindsight webhook 与全库补偿是后续扩展，不替代首版程序化直传；工具名均为设计，尚不存在运行实现。

## 既有系统边界

Herdr 本体承载角色与会话；协调语义归现任协调员/负责人，执行检查点归项目 workflow，审批记录归已有协调工具。Task Mailbox 保留持久传输、事件及版本，原 Project/Issue 保留事实和指定验收者结论。云端Dot发起、观察和汇报，不承担业务验收；项目默认由现任负责人验收。本服务是程序能力，不新增组织 Agent。[全局责任依据](https://github.com/CF-FE/herdr-4-codexcloud/blob/e43f6427dde563e08bdd0183a014b60f236f452c/docs/coordination-policy.md#1-默认分工与取舍)

workflow 的普通判断与用户审批入口分别接入，不能因都叫 decision 就互换。服务输出可帮助原 workflow 自动推进；原任务授权、计划应用、角色创建与业务验收不转移给模型结果。[已有工作流决定点](https://github.com/CF-FE/herdr-4-codexcloud/blob/e43f6427dde563e08bdd0183a014b60f236f452c/docs/project-workflow-development.md)

## 反馈回收与效果验证

MVP 的原适配器自动回传实际采用与工作单元结果，质量结论可稍后修订，不等角色退出。原检查点持久保留关联和待传事件；恢复时先只读原决定/动作/产物，再独立补传原事件。decide 后续报错不证明选择未保存，补传本身不得调用 decide/resume 或重跑业务。钩子尚未实现，不声称当前可自动恢复。

应用回收率与已知已结束单元的结果回收率分开，pending/missing/UNKNOWN 和质量待补单列；统计范围以原端清单/状态对账为依据。一执行关联多个 decision 时成本只算一次，累计快照与所含明细不叠加，模型/阶段分列，并发墙钟不相加。缺计量或归因不清保留未知。

质量复用原测试、产物检查与指定验收者结论，不给每次决策新增人工评分；建议被采用、技术结束、质量通过和效率更好分别记录。完整标签集、基线比较和 Hindsight webhook 随后完善，最小闭环不等待它们；[详细回收与效果合同](outcome-feedback.md)集中维护规则。
