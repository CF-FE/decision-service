# 总体架构与接口草案

状态：2026-11-08 评审迭代中的设计草案，未实现、未验收。保留独立公共能力方向，先验证一个场景的增益，再决定运行形态和接入范围。

## 设计取舍

统一规则版本、凭据、调用预算和评价方法有复用价值；但独立仓库、共享核心、独立进程、双入口和插件分发是不同决定。当前没有调用量、人工负担或对照效果证据，不能用“模型可调用”证明值得建设完整公共服务。

首期采用一个已绑定项目、一个明确判断问题、一个版本化输入快照和一个原调用方。确定性规则能回答的问题沿原流程处理；剩余语义判断才考虑模型。先比较现行方式、简单规则与模型的净收益，停止或缩减也是有效结论。HTTP/MCP 保持共用核心的目标，先实现真实消费者需要的入口；第二入口和插件按实际消费需求增加。

## 数据流

既有调用方提供权威来源快照 → 认证/项目授权 → 校验输入与配置适用条件 → 按场景可选 Hindsight recall → 精简证据包 → OpenAI Decisions API → 类型/枚举/阈值校验 → 返回带依据版本的建议 → 原调用方复核当前状态和既有权限后处理。

服务判断的是给定快照，不承诺持续掌握各项目实时状态。模型计算期间状态可能变化；采用建议前的版本、权限和业务硬规则检查由原系统负责，不能用服务早先的校验代替。已验证结果之后可异步沉淀为记忆；建议、采用动作和最终业务结果分别记录。

## 核心组件

- **决策配置目录**：预先审核的 decision_kind、问题、候选枚举、证据要求和阈值版本。场景定义由对应业务负责人维护，服务保存可追溯的发布版本；不另维护人员任职、项目注册表或批准账本。调用者不能任意替换系统规则或任意指定派发目标。
- **Evidence Builder**：输入最小化；记录事实来源、观察时间、状态版本、项目和作用域；标记缺失、过期和冲突。
- **Memory Adapter**：按可信项目映射选择 bank，过滤和限制检索；不能由不可信内容决定 bank 或权限。
- **Provider Adapter**：隔离 Decisions API 合同、模型配置、限流、错误和拒绝。模型、prompt、profile 版本要可追踪。
- **Policy Validator**：确定性检查接口权限、输入约束、返回类型和候选项；检查已明确映射的场景条件，不复制全部项目业务规则。
- **Decision Record**：保存输入与配置版本、实际送入模型的证据引用、返回结果、规则处置、耗时和成本，不取代业务状态库。
- **HTTP/MCP Adapter**：按消费需求逐步提供，共享相同核心实现与权限逻辑。

以上是职责划分，不要求分别做成模块、微服务或通用插件框架。

## 首批场景候选

| 场景 | 候选结果示例 | 不可越界 |
| --- | --- | --- |
| 项目路由 | 已注册候选 / unknown / review | 已有绑定直接复用；未知项目路由后置，见下节 |
| 自由文本辅助分类 | 进展说明 / 依赖说明 / 异常说明 / 交付声明 / 混合或未知 | 只补充语义标签，不覆盖原生事件类型或验收状态 |
| 证据缺口提示 | 缺少某类材料 / 来源冲突 / 待人工核查 | 文件是否存在、版本是否匹配先由程序检查；不证明产物合格 |
| 异常分流建议 | 匹配既有处理方案 / 需负责人 / 等待依赖 | 已知错误码先按规则；不决定授权或重试未知副作用 |
| 负责人关注度 | 普通 / 高 / 紧急 / 待复核 | 截止时间等已知规则优先；不自动对外发消息 |

示例枚举不是已上线协议。先列 3–5 个候选，再以频率、当前人工负担、可标注性和错误成本选一个首验场景；当前尚未完成选择。一个输入可能包含多种事件，须先定义判断单位，不能把不互斥的事实硬塞进单选。没有确定的语义缺口时，保留原规则流程。

结合全局系统源码，优先补证的候选是“一个已绑定项目内，未结构化阻塞说明 → 有限的下一项只读排查建议或辅助标签”，旁路挂在已有 workflow 的普通 decision 点。它不覆盖原生事件类型，不接管审批/验收，不发起重跑；实际频率和收益仍为 UNKNOWN。已知项目 ID、事件类型、错误码、版本/hash、期限和任职代次都先复用程序规则。

## 项目内判断与未知项目路由

首期项目内判断要求调用方已有可信项目绑定，project_id 经认证层允许后才使用项目证据和 bank。

未知项目路由不能先要求已知目标 project_id，也不能让模型猜出的项目决定读取权限。若后续启用，入口身份先限定可见的注册表候选与描述；模型仅在该范围内建议目标，默认不检索候选项目的私有 bank。目标选择后的数据访问与派发仍由原系统重新授权。路由作用域合同需单独明确，不能复用项目内合同并把 project_id 留空或设为全局通配。

## 建议的公共合同

以下为本服务自定义草案，不是 OpenAI 请求字段：

项目内请求包含 request_id、project_id、decision_kind、profile_version、subject_ref、state_version、observed_at、facts 与 evidence_refs。身份与角色来自认证层；若保留 caller_role，仅作为待核对的描述。状态快照须指向原权威来源；服务校验来源绑定和适用条件，不凭一个自报版本号宣称取得了最新状态。

响应包含 decision_id、request_id、disposition（suggested / abstain / needs_review / unavailable）、有类型的 answer、reason_codes、输入证据引用、profile_version、model、created_at 与输入摘要；回显所依据的状态和证据版本。配置版本须绑定问题、候选集和阈值，不能在相同版本下静默修改。

- 保留 provider 的 predicate / choice / score / refusal 类型及各自字段；probability、confidence、score 和 Hindsight 相对排名不合并成一个通用可信度。
- reason_codes 来自服务可验证的规则处置；evidence_refs 表示输入来源，不是模型返回的解释或证明使用过该来源的引文。需要自由文本理由的场景另行论证，不给有限答案 API 虚构能力。
- suggested 表示符合本场景返回建议的条件；abstain 表示无法形成建议；needs_review 表示回到原负责人或既有处理路径，不自动向用户申请批准；unavailable 表示依赖或计算不可用。无有效建议时 answer 为空，原始 provider 响应仅作受控诊断记录；模型 refusal 也不得变为正常候选。
- 认证失败、非法请求及 ID 冲突仍是接口错误，不能全部包装成“判断未知”。合法请求中的低把握、证据缺口和依赖故障有明确回退；禁止错误默认成通过。
- 决策计算无业务副作用，但可能产生模型费用和审计写入。幂等范围包含认证调用方、项目和 request_id；同 ID 的输入或指定版本变化应冲突。
- 服务受理后冻结输入及实际检索证据，同请求重试查回原记录，不重新检索后改写原建议；需要新证据时发起明确的新请求。首期不做跨请求结果缓存；后续若证明有益，键须包含权限作用域、状态、配置和证据版本。
- 不将固定 0.9 等阈值作为通用标准；阈值由每场景的错误代价和离线样本校准。

### 超时与查询

若提供 get_decision，须支持在原认证作用域内按 request_id 查询，不能要求调用方持有可能随首次响应一起丢失的 decision_id。先持久记录受理，再调用 provider；区分 processing、completed、failed 和 indeterminate 等处理状态与上述判断 disposition。

查询只恢复本服务已保存的记录。provider 请求可能已执行而结果无法确认或保存时，不能宣称原答案已恢复或恰好一次收费。纯判断可按已配置的次数、费用和总截止时间做有限重算，每次保留独立 attempt 及是否重新推理；不因低成本重算新增用户审批，也不将该策略用于业务动作重派。

重复入口请求只查询/复用原受理记录，不重置预算或另开重试链；由服务一处拥有 provider 尝试预算。一次完成的结果保持冻结，迟到尝试不覆盖已返回建议。预算耗尽仍无法确认则结束为 indeterminate，不无限保持 processing。processing/indeterminate 不提供可采用的 answer；unavailable 只说明当前无建议，不证明 provider 未执行。服务未受理、记录过保留期和重算记录的查询语义在接口合同中明确，实际执行方始终负责原业务 ID 对账和业务幂等。

## 最小工具面

- evaluate_decision：返回建议，不派发、不改业务。
- get_decision：按原 request_id 或已取得的 decision_id 查询受理状态、已保存结果、证据与版本；权限不弱于 evaluate。
- record_decision_outcome：后续可选适配入口，不要求项目双写。早期可人工关联有来源的样本评价；达到自动化需求后再从项目 bank 的原生 webhook 回收，所有启用的入口共享来源、版本与幂等校验。

工具名为提案，不代表已经存在。MVP 不暴露任意 Hindsight 管理/删除工具、shell、Herdr socket 或无限制 URL 抓取。

## 既有系统边界

Herdr 本体承载角色与会话；组织协调语义归现任协调员/负责人，执行检查点归项目 workflow，审批记录归已有协调工具。Task Mailbox 保留持久传输、事件及版本，项目原件与原 Project/Issue 保留事实和指定验收者结论。云端Dot发起、观察和汇报，不承担业务验收；项目默认由现任负责人验收。本服务是被调用的程序能力，不新增组织 Agent 或批准账本。[全局责任依据](https://github.com/CF-FE/herdr-4-codexcloud/blob/e43f6427dde563e08bdd0183a014b60f236f452c/docs/coordination-policy.md#1-默认分工与取舍)

业务推进权限不得从历史记忆、普通 Issue/评论或模型答案推导；原任务中的有效授权仍沿既有可信合同处理。workflow 的普通模型判断与用户审批入口分别接入，不能因都叫 decision 就互相替代。[工作流决定点](https://github.com/CF-FE/herdr-4-codexcloud/blob/e43f6427dde563e08bdd0183a014b60f236f452c/docs/project-workflow-development.md)

服务只引用原系统的项目、任务、事件和版本，不建立第二套业务 ID、任职关系、待办派发或业务动作重试循环。服务自己的 request/decision ID 仅标识判断计算。场景分类标签与原生事件状态分开；确定性权限和门禁由原程序检查，业务验收仍由原验收者负责。

## 异步结果回收扩展

评价方法从首个样本开始定义，自动回收设施按需求后置。采用自动回收时，项目 bank 保管结果原文；原生 webhook 通知服务，持久 inbox 去重后精确读取文档，关联原 decision，形成独立评价。补偿扫描不依赖语义 recall。详细合同、权限与启用门槛见[决策结果回收与验证方案](outcome-feedback.md)。服务处理账本仅保存必要处理与评价证据，不成为第二套业务/审批数据库。
