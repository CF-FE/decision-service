# ADR-001：独立公共决策服务与薄接入层

- 日期：2026-11-08
- 状态：设计提案，2026-11-08 经文档评审迭代；仓库与 Project 已按用户要求建立，修订方案未验收、未实施
- 范围：跨项目快速模型判断，不是用户审批系统

## 背景

Router 协调员、项目负责人和工作流需要共享快速分类、评分与候选分支判断，并利用 Hindsight 历史经验。仅靠各 Agent 的提示词会分散密钥、规则版本、审计和成本控制。

## 推荐决定

保留独立 decision-service 仓库与共享核心边界，先证明一个具体场景相对现行方式的增益，再确定最小运行服务与首个接入面。HTTP API 和 MCP 若均需要则共用逻辑；Skill 负责角色使用规范，插件在有安装分发需求时提供。服务化时优先评估现有 VPS，Mac/Windows 保留现有执行职责。

本次将“公共能力归属”与“运行形态和建设顺序”拆开。初始提案直接推荐轻量服务、双入口与 VPS；当前没有频率、负担和效果基线，先做有限离线比较更容易及早否定无收益场景。完整架构方向保留，未被证明必要的设施后置。[路线图](../roadmap.md)是该提案的验证顺序，不是开发授权。

## 替代方案

- 仅 Skill：不足以提供统一认证、模型调用和稳定程序合同。
- 仅 MCP：可服务 Agent，但工作流直接 API 调用更简单。
- 直接并入 Herdr：短期适配更少，但与跨项目公共能力目标耦合。
- 新审批平台：不采用，避免与既有用户授权、审批状态和执行检查点重叠。
- 先做有限样本与现行规则对照：推荐的验证起点，不能证明多消费者共享需求或生产效果；不把试验方式当作最终运行形态。
- 各项目嵌入 SDK：少一个网络跳转，但可能分散密钥、版本与运维；不作为默认推广方式。
- 立即建立独立服务和双入口：集中治理有价值，但未验证收益前会提前承担运维与适配成本；待首个消费者及隔离需求明确后选择。

## 后果与边界

- 新增独立服务的认证、版本、可观测与维护成本。
- 服务只提供模型建议及其证据，不产生用户批准或业务验收。
- 不更改 Herdr 已有审批 ADR，不将 OpenAI Decisions 与 Herdr approval decision 混用。
- Hindsight 是可选经验来源，不是实时权限/任务状态权威。
- 先影子运行，只有经验证的低风险分流才逐步自动化。
- 先比较现行方式与模型，再独立评估 recall 增益和反馈回收自动化收益；不把全量记忆集成作为价值验证前置。
- 统一判断记录不代表统一业务状态；原系统保有项目映射、授权、采用前状态检查、派发及验收责任。
- 任何部署、凭据与持久访问配置另在实施阶段核验授权。

## 待决

首验场景及收益判据、首个消费者与入口、运行形态、语言/框架、数据库、部署配置、域名、认证实现、场景阈值、回退预算和跨项目共享记忆范围。业务负责人/验收者按实际任职绑定确认，不能从仓库创建者或本次评审者推定。
