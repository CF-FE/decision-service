# 讨论沉淀（2026-11-08）

## 用户明确表达的目标

- 希望 Router 层协调员、项目负责人和项目工作流使用 Decisions API 做快速决策。
- 同时接入已有 Hindsight 记忆服务。
- 用户将其概括为“一套快速决策的公共服务”。
- 用户询问是否独立项目、部署在哪里。
- 用户要求在 CF-FE 组织新建仓库、沉淀本轮讨论，并创建对应 GitHub Project。

这些要求授权本次项目初始化与文档沉淀，不代表已经完成设计验收、实施、部署或凭据配置。

## 前期讨论推荐（历史）

1. 独立公共服务；仓库命名 decision-service。
2. 核心逻辑与传输层分离：HTTP API 面向工作流，MCP 面向 Agent。
3. Skill 定义角色调用规范；插件作为安装与分发形式。不是三选一。
4. OpenAI Decisions API 负责有限选项判断；Hindsight 按需提供项目历史经验。
5. VPS 优先承载服务；Mac 继续负责 Herdr 和任务执行接续；Windows 继续承担制作与现有 Hindsight 后端。
6. 先回放和影子模式，不立即自动改变业务。

以上为推荐方向，细节须经过本项目验收，尤其模型调用合同、权限边界、容量和阈值。

## 避免概念混淆

“模型 decision”和“用户 approval”不是同一件事。OpenAI Decisions API 是推理判断接口，不是可信真人批准、通知或 OAuth 身份验证服务。

协调系统可能使用 approval decision 等词，不能仅因名称相似就把模型结果注入受信批准入口。模型可辅助分类证据或推荐分流，但真实批准必须沿可信用户来源与现有审批合同处理。

## 选型理由

- 仅 Skill 难以统一密钥、调用成本、协议、限流、缓存和审计。
- 仅 MCP 不够覆盖确定性工作流的直接程序调用。
- 把一切塞进 Herdr 会令跨项目公共能力与单一协调实现耦合。
- 另建审批/执行平台会重复既有状态和责任边界。
- 每次都 recall、reflect、Decisions 会增加延迟，应依据任务决定是否检索。

## 尚未作出的决定

实现语言与框架、SDK 版本、存储引擎、缓存细节、超时预算、角色权限矩阵、模型阈值、服务域名及认证配置均未定。独立仓库不等于必须新买服务器，不承诺端到端毫秒级延迟或固定倍数加速。

## 首轮文档评审（历史）

用户要求先 review 项目文档、辩证分析并迭代更优方案，暂不急于开发；全局系统问题可向关联评审会话求证。本轮范围为方案与文档，没有运行服务、模型试验、部署、凭据配置或全局系统变更。

评审保留统一核心、项目隔离、建议与授权分离、独立结果评价的方向，并提出以下修订；它们仍是待验证设计，不是用户已接受的实现决定：

- 将价值验证前移：3–5 个场景作为候选，先用一个场景与现行规则/流程做有限比较，明确人工复核负担和停止条件。
- 将独立仓库、独立进程、部署位置、HTTP/MCP 双入口和插件分发拆开选择，按真实消费者需求投入。
- 分开项目内判断与未知项目路由；模型预测不决定 bank 权限，原系统保持注册表、任务和审批权威。
- 服务评价版本化快照，原执行器采用前检查当前状态与授权；补齐原 request_id 查询、处理未知及错误语义。
- 从首个样本开始评价，分别证明 recall 与反馈自动化的收益；完整 webhook 回收后置，启用后的证据和恢复要求保留。

以上保留首轮评审经过。其中“先证明收益再建设”“首期限单项目”“recall 先证明增益”等建议已由下述用户确认的新方向替代，不再作为现行前置要求。

## 用户确认的最新方向与补充

用户认为首轮修订过于保守，明确提出先做可跑通的 MVP，再迭代完善，并允许扩展访问其他 bank；随后确认“就按这个方向修订项目文档，先不开发”。因此取消前置价值验证、完整标签集、基线对照和逐场景 profile 审批，跨 bank 检索直接进入首版。基本联调确认链路能跑通，效果评估留到实际使用后。

用户进一步明确预期：提升工作流执行效率和模型 token 利用率；在动态工作流中快速判断如何调整、推进，在角色创建中按任务复杂度选择合适的模型类型和强度，并要求辩证完善。

本轮形成的具体设计是：workflow 提供当前状态与动作/计划候选，服务返回可直接消费的选择；需要新计划时沿原规划者生成候选，原执行器按原授权应用。模型选择先匹配模态、工具、上下文等能力，再按复杂度与预算选择预计足够的配置，按实质变化或质量反馈升降档。它们是待联调的实现方案，不代表运行系统已经具有任意改图或热切换模型能力。

跨 bank 采用一次静态范围配置，允许直接读取相关项目经验；不逐次审批、不默认扫全库，输入充分时可不检索。通用问题、预设和普通 prompt 迭代可直接进行，保留来源与实际版本；读取不自动扩展为其他 bank 写入/删除权。首版程序化反馈与主动纠正保存在服务记录中，完整 Hindsight webhook 回收后置。

用户要求与全局系统关联会话协作、双方文档互审，需要关联项目迭代的事项及时沟通。本仓维护决策服务合同与核心设计；Herdr/工作流侧维护候选生成、角色创建、计划与配置应用的接入文档及当前能力边界。双方在所属仓库修订并相互复核，不代改对方运行系统。本轮继续保持只改文档、先不开发。

双向互审已完成：Herdr 侧同步了工作流接入、角色模型配置、总体架构、共享记忆和状态五份文档；本仓核对了对应 diff 与工作流/Worker 源码。两端已对齐原 choice 导入、真实 source/input 摘要、冻结候选映射、非执行 needs_replan 出口和空模型候选处理。后续实现由本仓承接服务核心，Herdr 侧承接 workflow 薄适配与一条模型配置应用路径；实际运行中改图另由原 workflow 维护者扩展。具体接口入口见[双仓分工](architecture.md#双仓文档与接入分工)。这表示文档互审完成，不表示代码或运行验收完成。

现行方案以[架构](architecture.md)、[路线图](roadmap.md)和 [ADR-001](decisions/001-shared-decision-service.md)为准。方向采纳、文档互审、代码实现和运行验收分别记录；当前没有部署、模型试验、私有 bank 访问、角色创建或运行权限变更。

## 决策结果回收与效果验证补充

用户追问效果如何回收验证后，确认将讨论方案补进项目文档，并同步关联会话、双方互审，仍先不开发。MVP 增加原适配器自动直传 application 与 result；不是仅等用户手动评分，也不等待 Hindsight webhook 或全库扫描。

本仓[唯一详细合同](outcome-feedback.md)定义稳定事件与修订、decision_ids 和原工作单元关联、应用与结果两类回收率、质量待补及成本去重。Herdr 侧维护原状态持久关联、实际动作/配置与 usage 读回、待传事件及原恢复入口补传。查询保持只读，补传是独立步骤，不重新调用推进命令或重跑业务；原生字段缺失和效果未知不冒充未执行。

质量复用原检查/验收，不逐决策新增人工任务；角色按工作单元回收，不等退出。结果可后补质量修订，多决策不重复记一份执行成本；累计用量与所含明细不叠加，并发步骤不相加成整单墙钟。原端终态清单与缺口分别列示，关联不直接证明因果收益。

本轮双方已互审服务第0节主合同及 Herdr 消费者反馈/角色配置段落，应用已保存但后续推进失败、非原生关联、效果未知、取消生效、查询与补传分离等意见已对齐。相关文档修订表示合同一致，直传、恢复和汇总钩子仍未实现；本轮没有提交、部署或改变运行系统。
