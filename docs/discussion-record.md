# 讨论沉淀（2026-11-08）

## 用户明确表达的目标

- 希望 Router 层协调员、项目负责人和项目工作流使用 Decisions API 做快速决策。
- 同时接入已有 Hindsight 记忆服务。
- 用户将其概括为“一套快速决策的公共服务”。
- 用户询问是否独立项目、部署在哪里。
- 用户要求在 CF-FE 组织新建仓库、沉淀本轮讨论，并创建对应 GitHub Project。

这些要求授权本次项目初始化与文档沉淀，不代表已经完成设计验收、实施、部署或凭据配置。

## 讨论形成的推荐方案

1. 独立公共服务；仓库命名 decision-service。
2. 核心逻辑与传输层分离：HTTP API 面向工作流，MCP 面向 Agent。
3. Skill 定义角色调用规范；插件作为安装与分发形式。不是三选一。
4. OpenAI Decisions API 负责有限选项判断；Hindsight 按需提供项目历史经验。
5. VPS 优先承载服务；Mac 继续负责 Herdr 和任务执行接续；Windows 继续承担制作与现有 Hindsight 后端。
6. 先回放和影子模式，不立即自动改变业务。

以上为推荐方向，细节须经过本项目验收，尤其模型调用合同、权限边界、容量和阈值。

## 避免概念混淆

“模型 decision”和“用户 approval”不是同一件事。OpenAI Decisions API 是推理判断接口，不是可信真人批准、通知或 OAuth 身份验证服务。

协调系统可能使用 approval decision 等词，不能仅因名称相似就把模型结果注入受信批准入口。模型可辅助分类证据或推荐分流，但真实批准必须沿可信用户来源与现有审批合同处理。

## 选型理由

- 仅 Skill 难以统一密钥、调用成本、协议、限流、缓存和审计。
- 仅 MCP 不够覆盖确定性工作流的直接程序调用。
- 把一切塞进 Herdr 会令跨项目公共能力与单一协调实现耦合。
- 另建审批/执行平台会重复既有状态和责任边界。
- 每次都 recall、reflect、Decisions 会增加延迟，应依据任务决定是否检索。

## 尚未作出的决定

实现语言与框架、SDK 版本、存储引擎、缓存细节、超时预算、角色权限矩阵、模型阈值、服务域名及认证配置均未定。独立仓库不等于必须新买服务器，不承诺端到端毫秒级延迟或固定倍数加速。

## 文档评审迭代（2026-11-08）

用户要求先 review 项目文档、辩证分析并迭代更优方案，暂不急于开发；全局系统问题可向关联评审会话求证。本轮范围为方案与文档，没有运行服务、模型试验、部署、凭据配置或全局系统变更。

评审保留统一核心、项目隔离、建议与授权分离、独立结果评价的方向，并提出以下修订；它们仍是待验证设计，不是用户已接受的实现决定：

- 将价值验证前移：3–5 个场景作为候选，先用一个场景与现行规则/流程做有限比较，明确人工复核负担和停止条件。
- 将独立仓库、独立进程、部署位置、HTTP/MCP 双入口和插件分发拆开选择，按真实消费者需求投入。
- 分开项目内判断与未知项目路由；模型预测不决定 bank 权限，原系统保持注册表、任务和审批权威。
- 服务评价版本化快照，原执行器采用前检查当前状态与授权；补齐原 request_id 查询、处理未知及错误语义。
- 从首个样本开始评价，分别证明 recall 与反馈自动化的收益；完整 webhook 回收后置，启用后的证据和恢复要求保留。
