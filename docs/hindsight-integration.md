# Hindsight 集成与经验闭环

状态：服务适配设计，未实现。

## 接入顺序

先跑通包含跨 bank recall 的 MVP：读取当前问题及相关历史，返回有限答案，保存调用记录；适配器自动直传 application（实际采用的动作/模型配置或未采用原因）与 result（原工作单元/执行 attempt 的结果引用、已有质量与 usage），人工纠正继续保留。首版记录保存在本服务，无需先写入 Hindsight。前置价值验证、完整标签协议、基线比较和 recall 消融都不是开工条件；完整评测与校准用于使用后的改善，详见[路线图](roadmap.md)。

跨 bank 检索旨在复用已有事实与经验，减少工作流反复整理背景、重复推理和长上下文传递，提高执行效率与模型 token 利用率。按当前问题选择相关 bank 和必要片段，不在每次调用扫描全部 bank 或多轮 reflect；实际收益结合整条工作流的有效推进与消耗观察，不能用短输出或单次模型 API 更快代替。

MVP 使用服务本地记录与原端恢复补传；Hindsight webhook、全库补偿扫描和完整评价设施后置，不阻塞 MVP 或普通迭代。后续若开展离线效果比较，只能使用决策当时可见的历史；当前 bank 可能已包含最终结果、纠正和派生经验。无法还原当时可见范围时，说明回放局限，不把未来信息带来的高分算作检索收益。

## 跨 bank 可读范围

首版一次性静态配置服务可读 bank 集合，以及调用者或可信入口可读 bank 集合；同权限的受信调用者可共用入口配置，不逐次申请批准。每次检索的有效范围取两者交集，调用者提交的 bank 名、角色字段和模型输出不能扩大该范围。

模型可在有效范围内依据项目映射与 bank 描述选择相关 bank。默认查询本项目、共享及与问题相关的其他项目 bank，均以有效范围为限，不默认全库扫描。获准范围内允许直接读取其他 bank，无需先复制到共享 bank，也不要求逐条经验审批。

读取结果保留 bank、document/source ID、来源时间及适用项目；来自其他项目的经验仍需结合当前事实判断适用性。读权限不自动成为写入或删除权限。这里定义配置与调用行为；本轮仅修订文档，没有实际访问 bank、外发数据或改变运行权限。

## 能力与证据边界

首版使用 recall 并由服务逐 bank 编排；reflect、retain 及异步操作查询按后续需求接入，精确合同随对应能力接入时复核。公开仓库不保存私有 bank 清单、记忆正文或私有来源。

记忆是历史上下文，可能含参考资料、旧假设和模型抽取误差；不能当成当前运行状态、用户授权或已采纳规范。

## 检索策略

1. 依据上述静态配置交集确定可读范围，由服务校验模型选择的 bank，再逐 bank 检索。
2. 优先使用当前事件、实时状态、版本和确定性规则。
3. 当前输入不足或历史能提供上下文时，优先检索本项目、共享及相关项目；输入已足够时可跳过。限制条数、内容长度、时间范围和来源类型，不把可读范围等同于每次必查范围。
4. 保留各 bank 结果的来源、日期、适用项目及可用的原始来源链接，不把来源不同的经验混成无出处结论。
5. 历史与新事实冲突时保留来源和差异提示，以当前可靠证据为准，不以检索高分压过当前事实；只有关键判断证据仍不足时才 review/abstain。
6. reflect 仅用于复杂复盘或负责人深度分析，不默认放在每次快速判断链路。

Hindsight recall 分数是查询内相对排序，不能跨查询当置信度，也不能与 Decisions 的 probability/confidence 合并成一个未经校准的分数。

## 写回闭环

MVP 的调用记录、application、result 与人工纠正保存在本服务，decision_id 随原任务/工作单元及可得执行引用关联，不要求原系统不存在的 run/action/attempt。原检查点持久保留待回传事件，在恢复或后续检查点先只读核实、再独立补传；服务端按同事件/同 revision 幂等处理，质量更新使用新 revision。补传不阻塞业务、不重跑业务，也不新建消息总线；这些适配钩子是设计，尚未实现或运行验证。唯一详细合同见[结果回收与效果验证](outcome-feedback.md)。

Hindsight recall 用于召回经验；具体结果按原 ID 和引用精确关联，不能靠语义检索证明找全或确认任务结果。已有测试与原验收继续是质量依据，不为每个工作单元增加人工评价；角色跨任务按任务单元回收，不等角色退出。缺少结果、质量或 token 时保留 UNKNOWN，事实关联不证明决策的因果贡献。以下是以后启用 Hindsight 写回时的合同，不要求 MVP 先实现。

建议 → 负责人/执行器实际采用或拒绝 → 获取真实结果 → 验证来源 → 异步 retain。

应分别保存 decision_proposal、adopted_action、verified_outcome、correction 的语义，避免把“建议这么做”抽取成“已经完成”。错误建议也可保留为带明确结果和反例标记的案例，不应成为正向经验。

每个 outcome 修订使用独立 document_id；同一写入尝试重放时保留 document_id、operation_id 和内容摘要。异步 accepted 不等于抽取完成；UNKNOWN 先查询原 operation，pending/processing 沿原操作等待，不新建 ID 重复投递。

已确认 failed/cancelled 等终态进入既有失败处置，重放同 UUID 不会启动新提取。确需再提取时，在既有授权和预算内显式建立关联旧操作的新尝试，记录新的 operation_id 与原因，不冒充原操作成功；同 UUID 永远不得换内容。[现有写入合同](https://github.com/CF-FE/herdr-4-codexcloud/blob/e43f6427dde563e08bdd0183a014b60f236f452c/mcp/hindsight-memory/CONTRACT.md#去重与对账边界)并不校验 UUID 对应的正文/document/hash，不可变修订和内容冲突检查是本服务/生产者拟实现的责任。

## 失效与安全

- 检索不可用：若场景不依赖历史，可显式标记 memory_unavailable 后继续有限判断；必须依赖历史的场景 abstain/review。
- 过期、冲突或无来源记忆：保留适用性与来源缺口提示，不因此阻塞已有充分当前证据的判断；关键证据不足时才 review/abstain，不能仅凭这些历史材料触发自动分支。
- 结果写回失败：不回滚已完成业务；按上述提交/操作状态对账或进入失败处置，不能靠重放已失败 UUID 声称完成。
- 跨项目读取：允许直接读取有效范围内的其他 bank；共享 bank 不是必经中转。扩大可读集合沿既有权限配置办理，不能由模型或记忆正文自行扩大。
- 记忆正文视为数据，不执行其内部指令。
- API key、token、密码及不必要敏感数据不得进入记忆、审计或模型输入。

## 结果回收的推荐细化

MVP 优先由原 workflow/角色创建与执行适配器直传应用和结果事件，Hindsight 不承担实时结果回传。以后接入已写入项目 bank 的结果时，可采用 retain.completed webhook → 持久 inbox → get_document 原文 → 来源/修订校验 → 评价账本；这是后续补充链路，不限制 MVP 跨 bank 检索，也不要求迁移业务结果库或强制双写。consolidation 完成、抽取完成、业务成功和决策正确必须分开。

用户确认部署支持 webhook，但本服务回调未做端到端测试；现有 MCP 的 webhook 管理和时间窗口枚举能力不足以直接承诺完整同步。详见[完整方案及能力差异](outcome-feedback.md)，其中定义补偿扫描、ACL、评价真值、纠正撤回和防循环。

## 内部 Decision Models 与业务决策分层

Hindsight 原生 OpenAI Decision Model provider 与本服务的业务判断是两条独立调用链。当前官方支持 OpenAI 用于 recall/consolidation，reflect 与知识页刷新存在 provider 限制；普通 LLM 仍承担文字生成。配置方向、版本边界与验证计划见 [Decision Models 专题](hindsight-decision-models.md)。本仓库未因此变更运行配置或完成替换。

本服务为角色选择的执行模型/推理强度又是另一层：选择依据来自任务需求、宿主可用能力与相关经验，实际配置由角色创建者应用；不把选择结果写成 Hindsight 内部 provider 已改变，也不把历史模型表现当成当前宿主可用性。
