# 路线图与验收

当前仅完成项目初始化、讨论文档和看板。2026-11-08 文档评审将价值验证前移；下述阶段均为提案，没有开始开发，也没有承诺日期或默认负责人。阶段是按证据决定投入的顺序，不是每个场景都必须建设全套设施。

## P0：收敛场景与证据

列出 3–5 个有限答案候选，先选一个已绑定项目内、确有语义判断负担且可标注的场景。优先核对现有结构化字段、注册表和确定性规则；它们已经解决的问题不重复交给模型。

场景卡至少写明：

- 当前调用方、原任务/事件引用、实际频率与人工负担；缺数据时标 UNKNOWN。
- 判断单位、当时可见的输入、候选项、混合/未知情况、误报与漏报代价。
- 现行方式和可行简单规则基线；希望减少的人工工作，以及新增复核负担。
- 标签协议：判断对象、权威证据、标注/验收主体、分歧处理和评价时间窗口。
- 数据使用范围、预算与延迟目标、继续或停止条件；具体值由场景需求确定，不套通用阈值。

验收：有一个可复核的场景卡和去敏样例，明确非目标与事实来源；不存在用模型代替用户批准或业务验收的任务。选不出有用场景时保留研究结论，不以建服务为默认出口。

## P1：最小离线价值验证

在明确样本、数据传输与调用预算的授权范围后，先核对实际 API 合同和账户可用性，再对同批样本比较现行方式/简单规则与不检索记忆的模型。小样本可用于及早淘汰方向，不视为生产效果证明；无需先开发通用评测平台、HTTP/MCP 服务或 webhook。

进入正式比较前冻结标签协议，并将开发/校准样本与最终保留评估集按业务对象/事件链隔离。prompt、阈值和检索策略在前者调整，方案冻结后才用后者报告效果；样本不足时只报告探索性结果。避免近重复样本及后续结果泄漏；只使用判断当时可获得的事实，之后核验的标签不能倒灌成模型输入。

比较各类误判成本、有效覆盖、abstain/review、人工复核时间、原业务单的总模型回合数、端到端 P50/P95 延迟和总成本，另列 API 自身耗时。保留全体输入数、规则解决数和模型请求数，比较整条路径；准确率须与现行基线一起报告，含样本数、分布、未知标签和不确定性，不能仅报告筛选后已返回答案的正确率。

验收：报告是否满足场景预先约定的收益与成本条件，允许“停止 / 仅保留规则 / 补样本 / 进入影子接入”。实际调用成功不等于方案有价值。若缺历史是主要失败原因，可单独做下述 P3-A 的离线对照，不必先实现整个集成阶段。

输入和授权已就绪的标签核对、API 合同小样本检查、无记忆基线和 recall 对照可独立安排；不以本路线图新增逐项审批或完整评测平台门槛。

## P2：一个消费者的最小影子接入

价值证据支持后，再确定最小运行形态和首个入口。实现无业务副作用的 evaluate/get，固定请求/响应、身份与项目隔离、配置版本、处理状态与错误语义。HTTP/MCP 共用核心，但只交付首个真实消费者需要的入口；Skill 和插件随明确使用与分发需求补充。

旁路接入只记录建议与原流程选择，不改变业务。调用方提供版本化快照；原执行器保有采用前的状态、权限与硬规则检查。同步收集有来源的人工抽样评价，记录 eligible 请求数、抽样方法与缺反馈，不把影子模式未采用的建议判成错误。

验收：正常、refusal、无效枚举、超时/响应丢失、跨项目访问、重复 ID 和冲突输入的行为明确；按原 request_id 可查本服务受理记录，无法恢复的 provider 结果保留未知。凭据不入日志，服务故障可回原流程，影子分布和人工负担有证据。

## P3：按收益分别接入记忆与自动反馈

两项是可独立推进的能力，不互为必经前置，也不要求先于所有低风险灰度完成。只为已启用能力承担其正确性和运维要求。

### P3-A：可选 recall

仅在场景需要历史时，比较同样本的“模型不检索”和“模型带检索”，包括检索额外成本、延迟、错误历史与信息泄漏。保留当时可用的记忆版本和来源；若无法重建历史可见范围，明确该回放不能证明线上增益，改用前瞻影子观察。

验收：有净增益才启用；bank 隔离、来源/日期、冲突记忆与离线降级成立；不默认 reflect，不将记忆排名当置信度。Hindsight 自身 Decision Model provider 的优化是独立议题，不作为业务服务前置。

### P3-B：可选结果自动回收

从第一阶段就评价结果，但只有反馈量、人工关联成本或漏件证据支持时才自动化。先确认既有项目结果发布方式；已写项目 bank 的结果优先沿原生 webhook 回收，不强制全部项目新增双写或迁移业务结果库。

启用时先核验 webhook、精确文档读取、读写 ACL 与补偿枚举，再做单项目影子回收。每修订独立 document_id，同修订重试保持 ID；通过[回收验收矩阵](outcome-feedback.md#8-实施阶段与验收矩阵)后才扩大覆盖。签名、持久化、去重、恢复、修订撤回与循环抑制不能因简化而省略。覆盖不足按有限范围报告，不以 2xx 代替闭环验收。

## P4：低风险灰度与部署

已有回放与影子证据满足场景目标，且容量、网络、身份和凭据安排成立后，选择一个可逆低风险分流场景。先限项目与流量，保留负责人路径，支持退回影子模式。不为普通低成本可复跑步骤新增统一人工审批门槛；是否需要审批仍沿原任务授权。

验收：灰度范围明确、版本可追溯、回退演练完成、未知状态不会重复业务执行，监控、成本预算及效果抽检可用。有第二个真实消费者时再验证复用程度、第二入口及分发方式，不把跨项目推广写成自然必然结果。

## 本次不做

不创建 API key、不安装服务、不部署 VPS、不修复现有 collector、不建立第二套审批系统、不自动写入 Hindsight 新经验、不启动真实业务派发。

## 评价反馈的发布门槛

覆盖率和反馈延迟先于单一准确率；区分执行结果与决策正确性，未采用/缺证据不能硬贴正确标签。普通带来源经验沿已有权限贡献；推广为共享规则、profile 或阈值时，经发布评审、独立保留集评估及影子比较再版本化采用，不因结果已写入 Hindsight 自动调整生产策略。
