# 路线图与验收

2026-11-08 用户已确认先跑通跨 bank MVP、再从实际使用中迭代；核心目标是提升动态工作流执行效率与模型 token 利用率。本轮只修订文档，尚未开发、部署或改变运行权限。下列是未来建设顺序，没有承诺日期或默认负责人。

不以前置收益证明、频率统计、完整标注集、基线对照或 recall 消融阻塞 MVP。基本联调确认链路能跑通，后续评测帮助改进效果。

优先记录推荐及实际模型类型/型号和推理强度；消耗数据优先级低，只附现有响应/回执中直接可得的 token、耗时等值，缺失留省略/null（不是0）。现金费用与等价估价不记录；不要求首版接通专门的 Harness usage 采集，不因缺消耗阻塞联调或反馈接收。

## M1：跑通跨 bank MVP

一个进程、一份判断核心，以 HTTP API 为首版程序入口，按 Agent 实际接入需求提供共用核心的 MCP；交付轻量 Skill 使用规范，Herdr/项目侧交付原流程适配器，插件分发后置。首版持久存储已确定为 SQLite，交付与记录范围见[架构](architecture.md#对外交付物)和 [ADR-002](decisions/002-mvp-deliverables-and-sqlite.md)。最小能力包括：

- 通用 evaluate：受信调用方提交问题、候选与上下文；常用问题保存为预设，不逐场景审批。
- workflow_next_action：根据任务状态选择下一合法操作、分支或具体调整方案，返回执行器可消费的候选及参数。
- role_model_selection：从宿主实际可用的模型/推理强度组合中，先满足能力需求，再按任务复杂度选择预计足够的配置。
- 跨 bank recall：一次配置服务与入口可读范围，显式或自动选择相关 bank；允许直接读其他项目 bank，不必先汇总到共享库，输入足够时可跳过检索。
- SQLite 记录与查询：保存冻结输入/候选、来源与结果、判断尝试、服务模型及推荐/实际执行模型配置、反馈修订和原工作单元关联；可得 usage/耗时附带，支持预算内重试，不先建完整后台恢复平台。
- 程序化反馈与纠正：适配器直传 application/result，精确关联实际采用、工作单元结果与已有质量；支持同事件重投、后补修订、原端恢复补传，人工纠正仍可用，不要求先写 Hindsight 或建设完整评价平台。

用一个真实 workflow 的少量例子同时跑通“下一步怎么推进”和“创建角色前用什么模型/强度”。项目路由及其他有限问题可直接复用 evaluate，不必先证明唯一高频场景。工作流调整由既有动作或具体候选计划表达；先消费已有合法分支，有限重排在原执行器支持处应用。原系统不支持的计划更新方式需明确交其维护者承接，不能以推荐结果代替真实应用。

首版的双仓配套工作分别为：本仓提供判断、跨 bank 检索及反馈幂等修订/关联汇总；Herdr/项目 workflow 侧提供 choice 适配、实际模型配置读回、application/result 生成及原状态持久关联和恢复补传。当前模板尚无这些反馈钩子，也没有通用并行/回退/运行中改图；原宿主配置应用与后续扩展在对侧文档维护。不能只返回建议便宣布两端已接通。

MVP 跑通检查：请求可达；至少一条跨 bank 端到端调用完成；一次所选分支经原 decide 实际推进检查点，一条模型/强度配置经原生创建入口实际采用并取得回执；两类程序反馈自动收回并关联结果，稍后的质量修订不被去重吞掉。同事件重投不重复记用量，原端中断后的补传不重跑业务；这些可用隔离工程样例核对，不需中断生产。空结果、部分 bank/模型失败及回收缺口可见，读取不扩大为写/删权限。不以准确率、收益或消耗数据齐全作为完成门槛，也不以只能解析推荐代替两端跑通。

HTTP 暴露 evaluate_decision/get_decision/record_decision_feedback 对应能力；提供 MCP 时核对两入口读写同一记录、重投不重复接收。Skill 与实际入口一致，消费者不直接访问 SQLite；服务重启后仍可读回已确认的决策和反馈。具体路由、工具绑定、驱动与表结构随实现确定，本轮不生成可执行接口或数据库。

## M2：投入实际使用

让结果进入原 workflow 的普通决定点与角色创建入口，在已有授权内自动推进；不要求所有调用经过统一影子期或人工确认。对尚不宜直接应用的具体调整可旁路观察，其余已就绪工作继续。动作执行、运行状态、角色生命周期和业务验收保持原归属。

只在会改变下一步或模型配置的节点调用：首次任务/角色创建、分支歧义、新证据、依赖变化、质量不足或需要重规划。固定规则可决定的转换直接执行，同一输入和版本复用已有判断；不为每个节点完成或无变化轮询新增模型回合。

由适配器随结果记录模型类型/型号/强度与质量引用，不等角色退出；现成 token、耗时等可附带，取不到留缺省且不追补。已有用量按模型/范围去重，累计量不与已含明细相加，并发步骤不相加成整单墙钟。质量与结果回收继续推进，不为计量新增适配或遥测平台。

展示应用回收率、原端确认已结束单元的结果回收率与 pending/missing/UNKNOWN；分母来自原任务/检查点对账，不仅来自已收到反馈。原端与服务都保留待核缺口；回传失败只沿原记录补传，不阻塞业务或重跑动作。规则集中在[最小回收合同](outcome-feedback.md#最小反馈合同)。

## M3：按反馈完善

根据真实使用调整问题、候选动作、模型配置预设、相关 bank 选择、检索量和处置阈值。普通调整可在已有权限内迭代，记录实际版本和结果，不逐项追加发布审批、完整保留集或影子比较门槛。

优先看已记录的模型/强度、任务质量、推进、失败返工与纠正；有直接可得且口径可比的 token/耗时再辅助判断。模型能力不足或任务显著变难时调整配置；权限、网络、工具缺失先处理对应原因，不一律升档。模型切换按原宿主支持的方式应用。

需要量化比较时，再补现行方式对照、带/不带记忆比较、标签协议与阈值校准。正式效果报告将开发/校准样本与保留评估集按业务对象/事件链隔离，保留样本数、分布和未知标签；不能用调参样本证明最终收益。无法还原当时记忆范围时，用前瞻观察代替含未来信息的回放。这些是迭代工具，不回头变成开工门槛。

## M4：扩展接入与 Hindsight 回收

按实际需要增加更多动作/计划候选、模型配置策略、消费者、插件分发和运行可靠性；若首版未接 Agent，MCP 在出现需求时补齐，与 HTTP 共用核心及记录。不要求每项扩展先完成单独收益论证，也不预先建设全部设施。

MVP 的适配器直传已纳入 M1；以后需要从 Hindsight 自动回收时，再沿[结果回收方案](outcome-feedback.md)增加 webhook、持久 inbox、精确读取与补偿扫描。两条路径复用原语义事件/修订避免重复计量，不能保留关联时同一结果范围只用一条路径。既有项目结果无需迁移或强制双写，不因扩展阻塞不依赖它的调用。

Hindsight 内部 Decision Models 优化由记忆组件维护者处理，不作为业务 MVP 前置。普通经验按已有权限贡献；自动把反馈变为生产策略、扩大数据写权或改变业务授权，沿对应责任方处理，不由一次模型判断自行生效。
